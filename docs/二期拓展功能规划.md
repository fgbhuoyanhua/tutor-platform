## 一、老师资质真实性验证

### 1.1 现状与缺口

- `tutor` 表目前只有 `subject_id`、`grade`（辅导学段）、`price`、`introduce`、`status`，**没有任何"老师本人是谁、在哪所学校、什么专业"的信息**。
- 注册与发布只校验用户名、手机号唯一，不校验身份真实性。
- 管理员后台已有 `GET /admin/tutors/pending` 与 `PUT /admin/tutors/{id}/audit`，审核的是"资料是否合规"，**不是"人是否真实"**。

### 1.2 要解决的问题

老师自述"我是某某大学大二数学系"，平台无法核实，学生与家长只能凭简介判断，存在虚假身份风险。

### 1.3 数据层扩展

`tutor` 表新增字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `school` | VARCHAR(100) | 就读院校 |
| `major` | VARCHAR(100) | 专业 |
| `grade_level` | VARCHAR(20) | 年级（大一～研三） |
| `edu_email` | VARCHAR(100) | 校园邮箱（可选） |
| `cert_status` | TINYINT | 0 未提交 / 1 待审 / 2 已认证 / 3 驳回 |
| `cert_time` | DATETIME | 认证通过时间 |

新建 `tutor_cert` 表（证明材料，一名老师可多次提交）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT PK | |
| `tutor_id` | BIGINT | 关联 `tutor.user_id` |
| `cert_type` | TINYINT | 1 学生证 / 2 学信网在线验证报告 / 3 校园卡 / 4 校园邮箱 |
| `cert_url` | VARCHAR(255) | 图片或报告文件地址（私有存储） |
| `cert_no` | VARCHAR(64) | 学信网报告编号（类型 2 时必填） |
| `expire_date` | DATE | 报告有效期（类型 2 时必填） |
| `status` | TINYINT | 0 待审 / 1 通过 / 2 驳回 |
| `reviewer_id` | BIGINT | 审核管理员 |
| `review_note` | VARCHAR(255) | 驳回理由 |
| `create_time` | DATETIME | |

索引建议：`uk_tutor_cert_pending(tutor_id, cert_type, pending_flag)`（`pending_flag` 为 STORED 生成列，待审时为 1、否则 NULL），防止同一老师同一类证明重复堆积待审记录——沿用一期 `uk_slot_active` 的同一套思路。

### 1.4 业务流程

1. 老师首次发布资料前，必须提交至少一种证明，未提交则 `cert_status=0`，列表不展示。
2. 管理员在后台看到待审队列，逐条核对：姓名与证件是否一致、学校与专业是否对得上、学信网报告是否在有效期。
3. 通过 → `cert_status=2`，列表与详情页展示"已认证"标识 + 学校 + 专业；驳回 → `cert_status=3` + 理由，老师可重新提交。
4. 认证信息变更（换学校、升学）需重新提交，旧记录保留为历史。

### 1.5 真实性增强（优先级低于人工审核）

- **校园邮箱验证**：向 `@学校域名` 发验证码，维护一份可信域名白名单（如 `*.edu.cn`）。这一项比上传图片更难伪造，可作为"已认证"的加强标记。
- **学信网报告校验**：校验报告编号 + 有效期，过期自动降级为"待重新认证"。
- 不建议做身份证人脸核验：涉及敏感个人信息，合规成本高，一期二期都不做。

### 1.6 安全与隐私

- 证件原图存私有对象存储，**不落公网可读 URL**，只能管理员凭签名访问。
- 前台只展示结论（学校、专业、已认证），不展示证件图。
- 审核通过后原图保留必要期限（建议 6 个月）再删除，删除动作写入 `admin_log`。
- 明确告知老师：材料仅用于资质审核。

## 二、老师超时未确认：提醒 → 管理员介入 → 处罚

### 2.1 现状与缺口

- 后端**没有任何定时任务**（无 `@Scheduled`），订单一旦停在 `status=0 待确认`，不会被系统处理。
- `appointment` 没有提醒计数字段，无法判断"提醒过几次"。
- 没有违规记录表，无法累计"这个老师第几次不确认"。
- 关键副作用：`uk_slot_active` 会把该时段占住（`active_flag=1`），老师不确认也不拒绝，等于**把这格时段锁死**，其他学生约不了。

### 2.2 要解决的问题

学生下单后老师既不确认也不拒绝，订单长期挂着：学生干等、时段被占、无人处理。

### 2.3 计时与扫描

新增定时任务，每 5 分钟扫一次 `status=0` 且超过阈值的订单。阈值建议做成配置项（`application.yml` 的 `order.timeout.*`）：

| 阶段 | 默认阈值 | 动作 |
| --- | --- | --- |
| T1 | 30 分钟 | 首次提醒老师（站内消息） |
| T2 | 2 小时 | 二次提醒（站内 + 短信/订阅消息） |
| T3 | 12 小时 | 升级：进管理员"待介入"队列 + 提醒学生"老师未响应" |
| T4 | 24 小时 | 系统自动关闭订单，释放时段 |

扫描必须**幂等**：以 `last_remind_time` + `remind_count` 判断，同一阶段只触发一次，避免每 5 分钟重复轰炸。

### 2.4 提醒链路

1. 站内消息：复用 `message` 表，新增 `type` 区分"系统通知"，前端消息中心增加对应样式。
2. 短信 / 微信订阅消息：二期接第三方，先留接口位（`NotifyChannel` 抽象，先只实现站内）。
3. `appointment` 新增 `remind_count`、`last_remind_time` 两个字段。

### 2.5 管理员介入

- 后台新增"待介入订单"列表：超 T3 未确认的订单，显示老师、学生、时段、已提醒次数。
- 管理员可执行三个动作：再催一次 / 代取消（需填理由）/ 记一次违规警告。
- 所有动作写 `admin_log`。

### 2.6 处罚阶梯（建议值，后台可调）

按"自然月"统计老师的超时未确认次数（`tutor_violation` 累计）：

| 累计次数 | 处罚 |
| --- | --- |
| 1～2 次 | 记录警告，站内通知 |
| 3 次 | 降权：列表排序靠后，同时可接单数从 N 降到 N-1 |
| 5 次 | 冻结 7 天：禁止接单，已接订单不受影响 |
| 累计 8 次或严重情形 | 封禁：`user.status=0`，需管理员解封 |

新建 `tutor_violation` 表：`tutor_id`、`type`（1 超时未确认 / 2 频繁拒绝 / 3 差评）、`ref_id`（订单号）、`occur_time`、`penalty`、`status`。索引 `idx_tutor_time(tutor_id, occur_time)`。

### 2.7 与现有订单状态机的衔接（重要）

一期状态机是六状态五转移：`0→1` 确认、`1→2` 开始授课、`2→3` 完成、`0→4` 学生取消、`0→5` 老师拒绝。

自动关闭**不建议新增状态 6**，直接复用 `0→4 已取消`，另加 `cancel_reason`（`student` / `timeout` / `admin`）字段区分取消来源。理由：

- 不动状态机，前端、报表、测试用例都不用改。
- `status` 一旦离开 0/1/2，`active_flag` 自动变 NULL，时段自然释放——现有生成列已经解决释放问题，无需额外逻辑。

### 2.8 验收要点

- 单测：超时扫描幂等（同一订单同一阶段只提醒一次）；自动取消后该时段可被再次预约；违规累计到阈值触发对应处罚。
- 并发：老师不确认被自动取消的同一时刻，另一学生抢同一时段，只能成功一条（`uk_slot_active` 兜底）。

## 三、实施顺序建议

1. `message` 增加系统通知类型（最小改动，先跑通通道）
2. `appointment` 加 `remind_count` / `last_remind_time` / `cancel_reason`
3. `@Scheduled` 超时扫描 + 分级提醒
4. 超时自动取消（复用 `0→4`）
5. `tutor_violation` + 处罚阶梯 + 后台待介入列表
6. 资质字段扩展 + 材料上传 + 后台审核
7. 校园邮箱验证（可选增强）

前 5 步构成"履约闭环"，是二期的主线；第 6、7 步是"可信度建设"，可与主线并行。
